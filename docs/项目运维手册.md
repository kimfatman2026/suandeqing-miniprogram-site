# 算得清宣传网站：项目运维手册

## 1. 文档目的与项目边界

本手册用于维护“算得清”小微商家经营管理小程序的品牌宣传网站。网站为**静态前端项目**，负责展示品牌价值、产品能力、人物化使用场景、常见问题与小程序扫码体验入口；不包含用户账号、经营数据、订单数据或后台管理能力。

当前页面由首页 `/` 与使用场景页 `/scenes` 组成。页面依据“清蓝经营画报”方向构建，遵循品牌蓝承担主要操作、橙色提示待处理事项、绿色表达增长和利润的语义规则。所有数据截图与人物照片均为品牌传播或使用场景示意，不能误表述为真实用户经营结果或客户评价。

| 项目项 | 当前约定 | 维护要点 |
| --- | --- | --- |
| 前端框架 | React 19 + Vite | 页面组件位于 `client/src/pages/`。 |
| 样式体系 | Tailwind 4 基础 + 项目 CSS | 全局令牌在 `client/src/index.css`，场景页细化在 `client/src/pages/scenes.css` 与 `scenes-refine.css`。 |
| 路由 | Wouter | 新增公开页面时同步更新 `client/src/App.tsx` 与站点导航。 |
| 品牌资产 | 平台托管静态资产 | 生产页面通过 `/manus-storage/...` 地址引用，源文件由 GitHub 仓库 `assets/` 目录备份。 |
| 发布方式 | 项目版本保存后自动发布 | 每次有可交付改动后保存版本；不要将未检查的实验性修改作为正式版本。 |

## 2. 本地开发与质量检查

在项目根目录执行下列命令。开发环境用于热更新预览；提交前应至少完成类型检查与生产构建。

```bash
pnpm dev
pnpm check
pnpm build
```

`pnpm check` 用于 TypeScript 类型检查；`pnpm build` 用于验证页面、样式、静态资源引用与生产打包是否正常。若构建只出现包体积提示、但命令正常结束，可记录为优化建议而非发布阻塞项；若出现 TypeScript、Vite 或资源找不到的报错，则必须修复后再保存版本。

| 检查节点 | 必做事项 | 通过标准 |
| --- | --- | --- |
| 文案、导航或样式改动后 | 执行 `pnpm check` | 无类型错误。 |
| 新增页面或图片资产后 | 执行 `pnpm build` | 构建成功，图片地址可加载。 |
| 交付前 | 检查首页、`/scenes` 的桌面与移动端预览 | 文字与背景对比清晰；页面无横向溢出；导航与主按钮可用。 |
| 发布后 | 打开生产域名复查关键入口 | 首页、场景页、使用指南与扫码弹窗均可访问。 |

## 3. 内容与页面维护

首页主组件为 `client/src/pages/Home.tsx`，包含首屏、产品能力、首页场景摘要、使用指南手风琴、品牌介绍、二维码占位弹窗与页尾。使用场景页为 `client/src/pages/Scenes.tsx`，通过人物经营瞬间、经营便签和纵向轨迹讲述零售批发、餐饮门店与服务业的应用价值。

所有新增页面应保持“先结果、再变化、后行动”的信息顺序。每屏只保留一个高强调的主按钮；若修改数据表现，应使用“场景示意”“产品示意”或经过业务确认的事实，禁止添加虚构的客户头像、客户评价、星级、下载量、门店数量或经营绩效。

### 3.1 使用指南维护

使用指南内容定义在 `Home.tsx` 的 `guideItems`。问答宜保持短句、可执行、无压力的语气；每条回答应告知用户可以看什么、下一步做什么，不应作出未证实的产品功能承诺。

### 3.2 使用场景维护

使用场景内容定义在 `Scenes.tsx` 的 `industries` 与 `moments`。每个行业场景都必须包含人物工作瞬间、明确的行业标签、轻量产品价值便签与“使用场景示意”标注。若使用品牌自有照片替换通用场景图，应确保拥有使用授权，并更新 `assets/ASSET_MANIFEST.md` 中的来源和用途说明。

## 4. 图片资产维护

部署环境不应将大尺寸图片直接存入 `client/public/` 或 `client/src/assets/`。新图片应先保留在项目目录外的静态资产工作区，再上传至平台托管存储；代码仅引用上传后返回的 `/manus-storage/...` 地址。GitHub 仓库中的 `assets/` 是源文件与交付备份，便于迁移、审阅与替换，不参与当前项目的生产构建。

| 资产类别 | GitHub 备份目录 | 代码引用位置 | 替换注意事项 |
| --- | --- | --- | --- |
| 品牌与产品界面图 | `assets/product/` | `Home.tsx` 的 `ASSETS` | 保持现有纵向截图比例，避免用未经确认的演示数据替换官方素材。 |
| 算小胖首屏插画 | `assets/brand/` | `Home.tsx` 的 `ASSETS.hero` | 保留橘色圆润猫咪、白色肚皮和深棕算盘等身份锚点。 |
| 人物使用场景图 | `assets/scenes/` | `Scenes.tsx` 的 `SCENE_PHOTOS` | 仅作为场景示意使用；确保版权或授权条件清楚。 |
| 小程序二维码 | `assets/qr/` | `Home.tsx` 二维码弹窗 | 目前页面为明确标识的占位区；接入正式二维码后替换此位置。 |

推荐的替换流程如下：首先将原始文件放入静态资产工作区，例如 `/home/ubuntu/webdev-static-assets/`；随后使用 `manus-upload-file --webdev <图片路径>` 上传；将命令返回的完整 `/manus-storage/...` 地址更新到相应页面常量中；运行 `pnpm check && pnpm build`，检查页面预览；最后把原始文件与资产清单更新提交至 GitHub。

## 5. 正式二维码替换操作

网站当前的“打开小程序”弹窗使用**非可扫码的占位图形**，以避免误导访问者。正式二维码应为清晰的 PNG 或 JPG，并建议至少 600 × 600 px、保留白色静区。二维码接入后，弹窗应展示真实图片，并保留“打开微信，扫描小程序二维码”的说明。

实施时，在 `Home.tsx` 中新增 `QR_CODE` 常量并将 `qr-placeholder` 元素替换为带有明确 `alt` 文本的 `<img>`。图片上传后必须在微信中实际扫码验证，确认进入的是算得清小程序的预期页面。若二维码变更，应同时替换 GitHub 的 `assets/qr/` 文件并更新资产清单。

## 6. 发布、版本与回退

每次完成页面改动、检查并确认可以交付后，保存一个描述清楚的网站版本。当前项目启用了自动发布，因此成功保存版本后该版本会立即成为线上版本。版本说明应表达改动范围，例如“新增使用场景页面与人物场景素材”，避免使用“更新”“修复”等模糊词。

如果线上页面在最新版本后出现关键布局、资源或交互问题，应优先从项目管理界面的版本历史回退到最近一个已验证的版本，而不是通过破坏性 Git 命令处理。版本回退后需要重新检查首页、场景页、使用指南和扫码入口。

## 7. 常见排查

| 现象 | 优先检查 | 处理方式 |
| --- | --- | --- |
| 图片未显示 | `/manus-storage/...` 地址与上传结果 | 重新上传源图，更新页面常量并检查文件名与地址。 |
| 首页按钮未打开弹窗 | `Home.tsx` 中的 `guideOpen` 状态与查询参数 | 确认按钮使用 `setGuideOpen(true)`，跨页入口使用 `?open=qr`。 |
| 场景页无法访问 | `App.tsx` 的 `/scenes` 路由 | 确认 `Scenes` 已导入且路由存在。 |
| 手风琴无法展开 | `accordion.tsx` 与 `Home.tsx` 的 `Accordion` 属性 | 使用内置组件，确保 `type="single"` 与每项非空 `value` 对应。 |
| 移动端内容拥挤 | 页面 CSS 的 `@media (max-width: 720px)` 段落 | 优先检查图片高度、浮层位置、文字行高与横向溢出。 |
| 发布后与预览不同 | 最新版本记录与静态资源地址 | 检查是否保存了对应改动，并确认未把本地文件路径写入组件。 |

## 8. GitHub 备份约定

GitHub 私有仓库应保存项目源代码、`docs/` 内的运维资料、`assets/` 内的当前图片源文件与资产清单。不要上传 `.env`、密钥、访问令牌、用户经营数据、浏览器下载缓存、`node_modules/`、构建产物 `dist/` 或任何未获授权的人物照片。

每次视觉或图片调整建议采用一次聚焦的提交：先更新代码与资产清单，再提交对应的图片源文件，提交说明写明页面和资产用途。这样在需要还原某次视觉调整时，可以在代码、文案和图片之间保持可追溯的对应关系。
